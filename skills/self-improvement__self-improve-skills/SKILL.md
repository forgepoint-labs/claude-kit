# Self-improve skills

Analyze recent agent performance and propose evidence-backed updates to local companion skills.

## Overview

This is the self-improvement loop. It closes the feedback cycle: agents do work (triage, review, implement), humans correct or override the agent's output, and this skill harvests those corrections to make future agent runs better.

The improvement materializes as updates to **local companion skills** — repo-specific `*-local/SKILL.md` files that specialize the generic `agent-workflows` skills for this repository.

## Evidence sources

Gather evidence from the last 14 days (configurable via `.github/oz/config.yml`):

### 1. Triage overrides

```sh
gh issue list --state all --limit 100 --json number,title,labels,comments,closedAt,updatedAt
```

Look for:

- **Label corrections**: issues where a maintainer removed agent-applied labels and added different ones. The maintainer's labels are the ground truth.
- **Reopened needs-info**: issues where the agent asked follow-up questions but a maintainer removed `needs-info` and triaged directly — the questions were unnecessary.
- **Duplicate false positives**: issues the agent flagged as duplicate but a maintainer unflagged.
- **Missing follow-up patterns**: issues where the same type of follow-up question recurs across multiple issues — these should become a documented pattern.

### 2. Review feedback

```sh
gh pr list --state merged --limit 50 --json number,title,reviews,comments
```

Look for:

- **Overridden reviews**: PRs where the agent requested changes but a maintainer approved anyway — the agent was too strict or flagged something the repo considers acceptable.
- **Recurring nits**: the same style or pattern comment appearing across multiple PRs — these should become a documented norm.
- **Missed patterns**: PRs where a maintainer left a comment like "we always check for X" or "this pattern is preferred in this repo" — signals for the local companion.

### 3. Feedback comments

```sh
gh issue list --state all --limit 200 --search "@oz-agent" --json number,title,comments
gh pr list --state all --limit 200 --search "@oz-agent" --json number,title,comments
```

Look for `@oz-agent` mentions with feedback content:

- "stop flagging X" / "X is fine in this repo"
- "always check for Y when reviewing Z"
- "our convention is ..."
- "this label should be ..."

### 4. Closed-as-not-planned issues

Issues closed without implementation may indicate the agent's triage was wrong or the issue was a false positive for certain categories.

## Analysis procedure

1. **Collect** all evidence from the sources above.
2. **Classify** each evidence item by which companion skill it affects:
   - `review-pr-local` — style norms, paths to skip, recurring review patterns
   - `triage-issue-local` — label taxonomy additions, follow-up question patterns, heuristics
   - `dedupe-issue-local` — known-duplicate clusters
3. **Deduplicate** — if the same signal appears in multiple evidence items, consolidate into one proposed change.
4. **Validate** — each proposed change must have at least 2 supporting evidence items (different issues/PRs) to avoid one-off noise. Exception: explicit maintainer feedback via `@oz-agent` counts as sufficient on its own.
5. **Draft** the companion skill updates.

## Companion skill format

Each companion skill follows this pattern:

```markdown
---
name: <skill>-local
specializes: <skill>
description: Repo-specific <skill> guidance for <repo>. Only the categories declared overridable by the core <skill> skill may be specialized here.
---

# Repo-specific <skill> guidance for `<repo>`

This file is a companion to the core `<skill>` skill. It does not
redefine the output schema, severity labels, or safety rules.
It only specializes the override categories the core skill marks
as overridable.

## <Category 1>

- <Evidence-backed rule>

## <Category 2>

- <Evidence-backed rule>
```

## Output

1. For each companion skill that needs updating, prepare the diff.
2. If the companion file does not exist yet, create it from scratch with the template above.
3. If it already exists, merge new entries without removing existing ones.
4. Write a `self_improvement_summary.md` at the repository root documenting:
   - How many evidence items were analyzed
   - Which companion skills were updated
   - What specific changes were proposed and why (with links to the evidence issues/PRs)
5. Create a branch and open a PR with the changes:

```sh
git checkout -b oz-agent/self-improve-$(date +%Y%m%d)
git add .agents/skills/*-local/
git commit -m "chore: update local companion skills from agent evidence"
gh pr create --title "chore: self-improve agent skills" \
  --body "$(cat self_improvement_summary.md)" \
  --base "$(git symbolic-ref refs/remotes/origin/HEAD | sed 's@refs/remotes/origin/@@')"
```

6. If `.github/oz/config.yml` specifies `self_improvement.reviewers`, request review from those users.

## Safety rules

- Never modify the core skills — only local companions.
- Never remove existing companion rules — only add or refine.
- Each new rule must cite at least one specific issue or PR as evidence.
- Do not invent rules from general knowledge — every rule must be grounded in observed behavior in this repository.
- The companion may never change the parent skill's output schema, severity labels, or safety rules.

## Configuration

Read `.github/oz/config.yml` for settings:

```yaml
version: 1
self_improvement:
  reviewers: [maintainer-1, maintainer-2]  # who reviews self-improvement PRs
  base_branch: auto                         # branch to target (auto = default branch)
  lookback_days: 14                         # how far back to look for evidence
```

## When to run

- **Scheduled**: weekly via GitHub Actions cron (see `docs/self-improvement.md`)
- **On demand**: when a maintainer asks the agent to improve its skills
- **After feedback**: when `respond-to-feedback` determines the feedback is about skill quality

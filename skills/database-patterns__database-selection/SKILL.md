# Database selection guide

Use this skill to choose the right database for a workload. The right answer depends on data shape, access patterns, scale, and team familiarity.

## Decision matrix

### Relational / SQL (PostgreSQL, MySQL, SQLite)
**Choose when:**
- Data has well-defined relationships between entities (foreign keys, JOINs)
- You need strict schema enforcement and ACID guarantees
- Multiple tables need to cross-reference each other frequently
- You need transactions (all-or-nothing multi-step writes)
- You need full-text search, JSONB flexibility, or vector search in one tool

**PostgreSQL** should be the default. Only pivot when you have a reason to. Postgres can handle light NoSQL (JSONB), full-text search (tsvector/tsquery), and vector search (pgvector) — so it often eliminates the need for separate tools.

**SQLite** when you need an embedded database (ships with the app, no server), IoT, or edge deployments. Turso/Cloudflare D1 turn SQLite into a cloud DB for distributed use cases.

**MySQL/MariaDB** when the team already knows it well or when maintaining a WordPress/legacy system.

### Document / NoSQL (MongoDB)
**Choose when:**
- Data is highly unstructured or varies in shape across documents
- Schema changes frequently and you don't want migration overhead
- You're storing collections of self-contained objects (not heavily relational)
- The access pattern is mostly "get this document by ID" or "search within a collection"

**Avoid when:** You need heavy cross-collection JOINs — MongoDB can do them but it's not optimized for it.

### Graph (Neo4j)
**Choose when:**
- Data is defined by complex, multi-hop relationships (social networks, recommendation engines, fraud detection, org charts)
- You need to traverse paths between entities efficiently (shortest path, degrees of separation)
- Relationships themselves carry data (roles, weights, timestamps)

**Note:** Graph databases are specialized. You will almost always run one alongside a general-purpose DB (Postgres, MongoDB). Use a graph DB when relationships are the primary thing you query, not just a secondary concern.

### Key-Value (Redis, Valkey, Memcached)
**Choose when:**
- You need a cache layer in front of a primary database
- You need sub-millisecond reads for hot data (sessions, rate limiting, counters, feature flags)
- Data is simple key→value lookups, not complex queries
- Data is non-mission-critical or can be rebuilt from a primary source

**Redis/Valkey** for features beyond simple caching (data types, pub/sub, Lua scripting, persistence).
**Memcached** for pure in-memory caching with maximum simplicity and speed.

**A key-value store is almost never your primary database.** It supplements one.

### Columnar / OLAP (DuckDB, ClickHouse, Snowflake, Databricks)
**Choose when:**
- You need to run analytics, aggregations, or reporting across large datasets
- Queries are "what's the average X across 10M rows?" not "get user #47"
- You're working with data science, dashboards, or ETL/ELT pipelines
- Data arrives as Parquet, CSV, or other file formats

**DuckDB** for local/embedded OLAP (like SQLite but for analytics). Reads Parquet/CSV/S3 directly.

**You never use a columnar DB as your app's primary transactional store.** It's for analytical workloads alongside your OLTP database.

## ACID tradeoffs

ACID = Atomicity, Consistency, Isolation, Durability.

- **Financial transactions, inventory, user accounts** → need full ACID (PostgreSQL)
- **Analytics, telemetry, page views** → can relax ACID for speed (Redis INCR, DuckDB)
- **Caching, sessions** → durability is optional (Redis, Memcached — data can be rebuilt)
- **Document stores** → MongoDB provides ACID at the document level; multi-document transactions exist but are heavier

Don't over-engineer ACID compliance. Match the guarantee to the actual risk of partial failure.

## Read-heavy vs write-heavy

- **Read-heavy**: Add indexes, use caching (Redis), consider read replicas, use OLAP for reporting workloads
- **Write-heavy**: Minimize indexes (they slow writes), use bulk/batch writes, consider write-ahead logs, use queues (SQS/Kafka) to buffer writes
- **Mixed**: Optimize for hotspots. Cache the expensive reads. Batch the frequent writes. Don't assume — measure.

## When NOT to add a database

- If your current DB handles the workload, don't add another one for "architecture"
- Caching (Redis) is often a band-aid for bad queries or missing indexes — fix the root cause first
- PostgreSQL with JSONB can handle light document workloads without adding MongoDB
- PostgreSQL with pgvector can handle vector search without Pinecone
- PostgreSQL full-text search handles most search needs without Elasticsearch

## Meta-guidance

1. **Start with PostgreSQL** as your default. Pivot only with a reason.
2. **Familiarity matters** — a DB your team knows well beats a theoretically better one they don't.
3. **Be boring** — choose mature, well-supported databases for core infrastructure.
4. **Quality of drivers** — check that the SDK/driver for your language is well-maintained.
5. **Ops cost** — managed cloud databases (RDS, Atlas, etc.) are usually worth the premium over self-hosting.

# Convention review

Focused code review for engineering conventions. Your job is to catch pattern violations before a PR merges — not to debate style or suggest refactors unrelated to conventions.

## Scope

Review the diff against the repository's established conventions. Do NOT attempt to understand business logic; that's the human reviewer's job. Focus on patterns.

## How to discover conventions

Before reviewing, understand the repo's conventions by checking:

1. `CLAUDE.md` or `.claude/rules/` for documented conventions
2. Existing code patterns in the same directory as changed files
3. README files in the relevant packages/modules
4. `.agents/skills/convention-review-local/SKILL.md` for repo-specific checklist items

## Generic backend checklist

For every handler or service in the diff:

1. **Middleware/wrapper present** — uses the project's standard wrapper pattern, not raw handlers.
2. **Import conventions** — follows the project's module resolution (path aliases, barrel exports, etc.).
3. **Auth flow** — any handler touching scoped data uses the approved auth mechanism.
4. **Input validation** — validation middleware or schema validation applied, not inline checks.
5. **Structured logging** — uses the project's logger, not `console.log`.
6. **Response helpers** — uses the project's response builder, not hand-built response objects.
7. **No PII in logs** — check logger calls for sensitive data.
8. **Types** — handlers use proper event types, not `any`.

## IaC checklist (CDK / SAM / CloudFormation)

9. **Builder/helper used** — not raw constructs when the project has a builder.
10. **Resource placement** — in the correct stack/module per project conventions.
11. **VPC attachment** — only when the handler needs VPC resources.
12. **IAM scoped** — by prefix, never `Resource: "*"` with sensitive actions.

## Frontend checklist

13. **Correct package manager** — matches the project (pnpm, yarn, npm).
14. **Component library** — uses the project's UI library, not a different one.
15. **State management** — uses the project's state approach (TanStack Query, Redux, Zustand, etc.).
16. **Path aliases** — consistent with project config.
17. **No mixed UI frameworks** — don't introduce a second component library.

## PR conventions checklist

18. **Branch naming** — follows the project's branch naming convention.
19. **Commit messages** — conventional commits or the project's commit format.
20. **PR body** — has the required sections (What / Why / Testing / Risk or equivalent).
21. **Target branch** — correct for the change type.

## Repository-specific overrides

The consuming repository may ship a companion at `.agents/skills/convention-review-local/SKILL.md`. When present, read it and apply its additional checklist items. The companion adds items but cannot remove the generic checks above.

## Output format

1. **Summary** — 1-2 sentences on overall convention health.
2. **Blockers** — pattern violations that must be fixed (numbered, with file + line refs).
3. **Warnings** — minor issues or suggestions (numbered).
4. **Looks good** — conventions correctly applied (brief bullet list).

Always cite specific file + line. Do not invent issues — only flag things visible in the diff.

## What you don't do

- Don't review business logic correctness (that's the human).
- Don't suggest large refactors.
- Don't debate style preferences outside the conventions.
- Don't approve or reject PRs — you produce a review, the human merges.

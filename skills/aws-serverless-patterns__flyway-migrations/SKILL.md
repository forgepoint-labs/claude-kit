# Flyway SQL migrations

Patterns for safe, reviewable database schema evolution with Flyway.

## File naming

```
db/migrations/
├── V001__initial_schema.sql
├── V002__add_order_table.sql
├── V003__add_order_email_index.sql
└── V{n}__{snake_case_description}.sql
```

Rules:
- **Version prefix**: `V` + zero-padded integer (3 digits minimum)
- **Double underscore** separates version from description
- **snake_case description** — lowercase, no spaces
- `.sql` extension

If someone else lands your version number first, bump yours (Flyway fails on duplicates).

## Idempotent SQL

Migrations run exactly once per DB, but write idempotent SQL for resilience:

```sql
-- ✅ Idempotent
CREATE TABLE IF NOT EXISTS orders (...);
CREATE INDEX IF NOT EXISTS idx_order_email ON orders(email);
ALTER TABLE orders ADD COLUMN IF NOT EXISTS notes TEXT;

-- ❌ Not idempotent
CREATE TABLE orders (...);
CREATE INDEX idx_order_email ON orders(email);
ALTER TABLE orders ADD COLUMN notes TEXT;
```

## Destructive migrations

`DROP TABLE`, `DROP COLUMN`, and data-mangling `UPDATE`s are destructive. Requirements:

1. Flag in PR title: `[DESTRUCTIVE]`
2. Second reviewer required
3. Backup verification: link to the snapshot taken before deploy
4. Rollback plan in the PR body
5. Run in the lowest environment first; only promote after verifying

## Safe NOT NULL column addition (3-step)

```sql
-- V010: add column nullable
ALTER TABLE orders ADD COLUMN IF NOT EXISTS notes TEXT;

-- (deploy code that writes to notes)

-- V011: backfill
UPDATE orders SET notes = '' WHERE notes IS NULL;

-- V012: enforce NOT NULL
ALTER TABLE orders ALTER COLUMN notes SET NOT NULL;
```

## Common patterns

### New table
```sql
CREATE TABLE IF NOT EXISTS order_note (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_key TEXT NOT NULL,
  order_id UUID NOT NULL REFERENCES orders(id),
  note TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS idx_note_order ON order_note(order_id);
CREATE INDEX IF NOT EXISTS idx_note_tenant ON order_note(tenant_key);
```

## Golden rules

- ✅ One migration = one purpose. Keep them small and reviewable.
- ✅ Idempotent SQL (`IF NOT EXISTS`, `IF EXISTS`).
- ✅ Multi-tenant tables always have a tenant key column + index.
- ✅ Include an index for every foreign key.
- ✅ Destructive migrations go through extra review.
- ❌ Don't edit a previous migration — write a new one.
- ❌ Don't put application logic in triggers. Keep business logic in application code.
